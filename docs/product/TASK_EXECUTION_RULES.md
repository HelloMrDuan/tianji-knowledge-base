# 天机平台｜一任务一闭环执行制度 V1.0

> 自 2026-10-11 起，**每次推进只选择一个能独立验收的 TJ-xxx.y 子任务**。每完成一个任务，就必须同步更新[任务状态表](TASK_STATUS.md)、[不可覆盖的变更日志](TASK_HISTORY.md)和必要的[父任务台账](EXECUTION_LEDGER.md)。不能以口头回复代替 Git 记录。  
> 具体任务范围、文件、验收见[92 项 WBS 详细计划](DETAILED_DELIVERY_BACKLOG_V1.md)；[最初设计基线](ORIGINAL_DESIGN_BASELINE_V1.md)始终优先。

## 1. 每一轮只解决一个真正可完成的任务

1. **领任务**：优先从 `TASK_STATUS.md` 按计划顺序选择首个前置依赖满足的 `TJ-xxx.y`。每轮只有一个主 ID、一个清晰交付结果和一个可重复验收标准。不要顺手把不相关的第二项记为完成。
2. **发现范围过大先拆分**：一个子任务仍需要多次迭代时，先在 WBS 新增更细的 `TJ-xxx.y.z`，给每一项独立目标、输入、输出、API/设计依赖、正反例和 DoD，然后只执行其中一项。拆分本身也需有追踪任务 ID，不能无限写计划。
3. **动手前标记**：把选中子任务设为 `进行中`，写明当前做什么、阻塞、关联真实 PR。其余任务状态保持不变。涉及两个仓库时，同一 ID 贯穿公开代码 PR 与私有知识/CI PR。
4. **真实开发与验证**：改代码、知识及 UI 时遵守证据/隐私边界、保留 #87/#89 古风设计；验证应含正例、反例、边界、真实 API/Playwright、必要时全量私有 Canonical。
5. **提交 PR**：同一任务 PR 附实际变更、`TASK_STATUS.md` 此 ID 最新状态与 `TASK_HISTORY.md` 一条**新增事件**；CI 不通过、PR 尚未合并，状态只能 `已提交PR` / `CI待验` / `阻塞`，不能 `已合并`。
6. **完成验收并关账**：公开/私有 PR 检查全部成功且确实合并后，用**同一 ID 的结账 PR**填写真实的 PR 链接、两个 `main` merge SHA、CI URL、知识/视觉判定和已知缺口，状态设 `已合并`；如真实部署验收成功才设 `已部署验收`。结账 PR 自身同样需要 CI 并合并。
7. **汇报和下一轮**：每轮最多汇报“本轮完成的单一子任务 + 验证凭证 + 仍未完成之处 + 下一个子任务 ID”。不把父任务或其他子任务借机标完。

## 2. 状态及其不可互换的含义

| 状态 | 真实意义 | 合法证据 |
| --- | --- | --- |
| `待做` | 已计划，尚未在本轮开展 | WBS 唯一 ID、验收标准 |
| `进行中` | 已实际修改或进行实测 | 当前分支/PR、目前障碍 |
| `已提交PR` | 真实 PR 已存在，检查仍不全 | 可打开的 GitHub PR |
| `CI待验` | 指定 head 的公开/私有检查尚未完成 | 真实 run URL、head SHA |
| `阻塞` | 缺来源证据、权限、外部服务或依赖 | 原因、解除前置条件 |
| `已合并` | **全部要求的代码、真实测试、必要私有证据和 PR 均成功合并 main** | 已合并 PR URL、完整 40 字符 main SHA、CI URL；不能仅有绿灯 |
| `已部署验收` | 已合并且生产/受控环境真实访问、权限、回滚通过 | 真实环境、时间、测试与回滚记录 |

**严禁**：将某个子任务的完成误记为整个 TJ 父任务完成；把研究候选当已授权；把截图生成当原始设计人工复核；把“CI 绿色”当“已经合并/上线”。

## 3. 每个原子任务必须有的字段

| 字段 | 必填内容 |
| --- | --- |
| 任务 ID | `TJ-xxx.y`，仅一个；父任务 `TJ-xxx` |
| 用户价值/产物 | 一个页面或 API 的真实用户变化，或一个独立知识/安全/测试验收产物 |
| 依赖和范围 | 实际文件、前置证据/知识版本、对应 UI ID、原版设计截图；不涉及注明不适用 |
| DoD 完成标准 | 正例/反例/边界、实际输出、数据与权限限制、真实 CI / 视觉验收 |
| 状态与负责人 | 待做/进行中/已提交PR/CI待验/阻塞/已合并/已部署验收；执行者/承接窗口 |
| 证据 | 公开 PR + merge SHA；必要私有 PR + merge SHA；Actions URL；真实运行日志摘要 |
| 日期与下一步 | 更新时间、还有什么缺口、下一个任务 ID |
| 追踪变更 | 每次状态变化都追加 `TASK_HISTORY.md` 事件，**只准追加、不允许改写旧事件** |

每次合并**至少**有一条状态变更事件；纯进度/文档调整也必须关联一个原子 ID。尚未满足验收的任务允许记录 `阻塞` 并把原始失败日志留存，但不得在汇报中宣称该任务完成。

## 4. 两个文件的职责及计算方式

- [逐任务状态](TASK_STATUS.md)：一项一行，初始共 **92 项**（原 91 项 + 本规则建设任务 `TJ-001.4`）。列出当前状态、证据、日期和下一步。要确认进度，**先看这一页**。
- [状态变更日志](TASK_HISTORY.md)：每个事件只归属一个 ID，按序增加 `E0001` 等编号；记载状态变化、PR、CI、阻塞、实际结果和未来任务。**历史事件不能改写或删除**，历史记录误写需增加纠错事件。
- [父级执行台账](EXECUTION_LEDGER.md)：汇总 M0～M7 的父任务、合并交付和主要风险。任何父任务的子项尚未满足全部 DoD，则父任务仍是 `进行中` / `阻塞`。
- [详细 WBS](DETAILED_DELIVERY_BACKLOG_V1.md)：任务定义唯一依据；状态表中的 ID 集必须与 WBS 完全一致。任何新增/拆分要同步调整 WBS 和状态表，新增项初始状态为 `待做`，不能虚构完成。

## 5. 自动检查与真实局限

`scripts/check_task_tracking.py` 在公开 GitHub PR 检查中验证：

1. 状态表 ID **唯一**，并与 WBS 子任务列表完全一致。
2. 状态值合法；完成态必须附可核验 PR 链接、40 位 SHA 和 CI URL；未完成态不能滥填 merge SHA。
3. 事件编号连续、事件 ID 在状态表存在；同一事件的状态与该任务最新状态相同；已完成历史的事件不得被篡改。
4. **基线建成之后的普通 PR**：对比 base/main，必须恰好改动**一个既有任务的状态或证据**（或新增一个任务），并且只追加一条匹配的事件，不允许两个 ID 在一个 PR 中同时关账。漏更新就失败。
5. 初次建立机制的 `TJ-001.4` PR 属基线特例：它会一次录入既有 91 条计划、历史合并证据；这一例外只允许在 base 完全不存在状态表时触发，后续不再允许。

**限制**：GitHub Actions 自动校验格式、关联和追加性，不会伪造或替代真实 CI、人工设计验收，也不能仅凭提交的 SHA 字符串证明 GitHub 上真的合并。合并凭证需要人工/连接器核实后写入；当已完成任务的历史资料证据不足，必须保持待核实并补证据。

## 6. 单任务执行回执模板

```text
【当前任务】TJ-xxx.y · 任务标题
【目标】具体用户或知识资产变化：
【改动】实际文件和 public/private PR：
【验证】正/反/边界、真实 API、公开/私有 CI：
【状态】待验 / 已合并 / 已部署验收 / 阻塞：
【已合并 SHA】公开：___；私有：___ / 不涉及
【证据】Actions、截图（原始 #87/#89 对照）、Rule/Evidence：
【遗留】未覆盖的场景、风险与下一项 ID：
【记录】TASK_STATUS.md 已更新；TASK_HISTORY.md 新增事件 E____
```

未来如果遇到大规模紧急安全修复，允许先修再补记录，但应在**同一修复 PR**里附原子 ID 及事后真实验证；不得因此给一般开发开绿灯。
